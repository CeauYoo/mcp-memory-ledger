# Offline memory evaluation and capacity observations

This is a technical MVP diagnostic suite. It does **not** establish improved real agent task success, model reasoning, token savings, authenticated feedback, or production capacity. It invokes no paid/network model. Synthetic fixtures are not representative of user traffic.

## Fixed selection before tuning

`tests/fixtures/memory-evaluation/tasks.json` is the fixed v1 selection: ten bilingual cases, eight literal queries (including short Chinese, identifiers, punctuation, ASCII case) and two intentionally unsupported paraphrases. Every case includes a foreign-scope lexical duplicate, an initial observation/Claim, synthetic external feedback, and a correction. Keep this selection unchanged when comparing builds; report the SHA-256 emitted by the harness. Add future selections as new versions, do not remove failing cases or tune this fixture into a training set. The two paraphrases remain in aggregate results and are additionally reported as a separate stratum.

`query-scenarios-v1.json` adds 50 fixed query scenarios over those same ten tasks: full/partial literals, OR-with-missing terms, literal quotation characters, and no-literal-match queries. These are not 50 independent tasks. They were added after the initial ten-task implementation as contract coverage, so they are not held-out quality evidence. Raw-recall results, expected hits, ranks, latency and response bytes are saved separately in `query-scenarios.json`; the original task matrix stays unchanged.

The oracle is the fixture's initial/corrected Claim identity, not the retrieval implementation itself. Context Recall@k (after packing, not raw candidate retrieval) divides relevant returned IDs by the number of relevant IDs; reciprocal rank is 1 / first relevant position, otherwise zero. Gold Claim identity changes after correction; no-memory has the same before-correction gold identity as B. This measures relevant record retrieval, while the separate stale-answer proxy tests whether the original value is still used. There is one relevant Claim per task in v1. An observation containing an old value is historical evidence, not an active conclusion.

## Reproduce

Build the intended binary with the repository's pinned Rust toolchain, then run:

```sh
cargo build --bin agent_llm_mm
python3 scripts/evaluate-memory-loop.py --binary target/debug/agent_llm_mm --output target/reports/memory-evaluation
python3 -m unittest discover -s tests/fixtures/memory-evaluation -p 'test_*.py'
python3 scripts/benchmark-memory-capacity.py --binary target/debug/agent_llm_mm --output target/reports/memory-capacity --label exact-commit-and-build-profile
# Optional separate actual dashboard HTTP concurrency phase (mock, loopback only):
python3 scripts/benchmark-memory-capacity.py --binary target/debug/agent_llm_mm --output target/reports/memory-capacity-http --label exact-commit-and-build-profile --dashboard-http
```

On Windows select `python` and the `.exe` binary. Python scripts require only the standard library. The benchmark uses Python SQLite with FTS5/trigram support when the selected binary creates a trigram index. SQLite versions are reported. All database files are created under a fresh temporary directory and removed on exit; no user database argument exists. Results require an empty output directory and never overwrite prior evidence. For historical binaries without the new candidate/experience tools, pass `--legacy-supersede` explicitly; the report labels the legacy correction path and absent E checks. Default evaluation requires the new tools and fails if unavailable. The mock configuration is explicit and caller `AGENT_LLM_MM_*` variables are removed. Reports contain synthetic data only.

## A/B/C and single-component ablations

- A: no retrieved context; the deterministic selector abstains.
- B: initial ledger plus bounded recall, before external feedback/correction.
- C: the same ledger, synthetic `tool_reported` external observations, get the exact target/version, propose and validate a persisted candidate, commit it with a durable retry receipt, and recall the new state.
- C minus correction: feedback is ingested, but the old Claims stay active. This removes correction alone; raw observations may disagree with Claims.
- C minus retrieval: corrected ledger remains but the selector receives no context.
- C minus byte budget: same corrected state/query/k, with the API maximum byte budget instead of the fixed 1800-byte budget. This is bounded by the API, not truly unlimited.

The answer selector simply picks the first returned Claim with an exact subject and reports its object. Exact-answer and stale-conclusion-use fields are **deterministic proxies**, not model success or real mistake rates. Correction proposals are supplied by the fixture rather than generated by a model; the suite does not measure whether a model chooses a justified revision. It checks correction replay, preserved superseded history, evidence provenance, scope isolation, and exact compact UTF-8 JSON context size. Both missing-evidence and nonempty-limitation proposals must be blocked, fail commit, remain rejectable, and leave their targets unchanged. The successful synthetic fixture reports an empty limitations list because it asserts an exact unrestricted value within the artificial fixture. This is not a claim about external reality. v1 conservatively rejects nonempty free-text limitations because their applicability cannot be proved deterministically; a separately reviewed general correction is a distinct path. The same real MCP run records a rich episode and exercises semantic and procedural experience through pending → active → revised pending → rejected → rolled-back new pending, preserving inspectable history and verifying only current active candidates enter recall. Procedure steps are never executed. It records latency but applies no invented latency/recall quality gate. Zero scope leaks, preserved references, and exact budget accounting are contract correctness assertions.

`report.json` includes aggregate and per-stratum means. `results.json` retains each context, returned IDs, answer selection, byte count and observed local MCP latency. `mcp-transcript.json` retains requests/results. UUIDs and timestamps vary; the fixture hash and oracle relations remain stable. Timing includes local MCP transport, retrieval and serialization, and is not model inference time. Bytes are not tokens. `model_task_success`, `token_usage`, and `token_cost` remain null rather than estimated.

## Optional future same-model adapter

`adapter-requests.json` exports task prompts, variants, contexts and fixture hashes for a separately authorized runner. Export is not permission to call a provider. The harness does not execute adapters or use API keys. `tests/fixtures/memory-evaluation/experiment-record.schema.json` defines the future result record.

For genuine experiments, freeze the dataset and evaluation rubric first; use the same pinned model/version, system prompt, tool/turn/output budget and sampling settings across variants; preserve actual prompt hashes and traces. Randomize/counterbalance variant execution order, repeat seeds/replicates, record failures and abstentions, and disclose any extra feedback/tool/model computation. Score held-out tasks independently of the mechanism under evaluation. Measure actual provider usage (including cached/reasoning tokens where available) and billed cost or an explicitly dated price calculation; leave unavailable values null. Do not label proxy rows as genuine model results. Provider calls, spending and any transmission need separate authorization.

## Capacity protocol and limitations

The default 10,000 / 100,000 sizes count events plus Claims, split evenly. Each includes twenty namespaces, a 100-Claim revision chain with 99 Reflection rows, evidence links, episode links, and any derived-index rows created by actual schema triggers. Direct SQL bulk seeding is reproducible synthetic preparation, **not application ingestion throughput**. Hashes cover exact event/Claim payloads and must agree between comparison builds.

The selected binary initializes its own schema. Queries run through real stdio MCP: selective ASCII, common two-character Chinese (literal fallback), a revision-chain query, and no-match query. Each query has two discarded warmups and twenty measured repetitions by default. p50 is the median; p95 is nearest-rank. Record response bytes, database bytes, Linux server RSS snapshots (not peak; null elsewhere), and observed timings. The three-client workload runs concurrent ingestion, recall, and dashboard-like `search_memory` browsing; it does not render a browser dashboard. A 50 ms external writer reservation measures end-to-end write delay or rejection, not internal lock-wait telemetry. No WAL/busy-timeout tuning is performed by the harness.

The opt-in `--dashboard-http` adds a separately labeled phase **after** those default measurements. It starts a mock-provider dashboard bound to `127.0.0.1`, with browser opening and SSE disabled, against the same disposable synthetic database. Each round runs ingestion, recall, and an HTTP worker concurrently; that worker reads `GET /api/summary`, namespace-filtered `GET /api/events?namespace=project%2Fcapacity-00&limit=20`, and namespace-filtered `GET /api/operation-log?namespace=project%2Fcapacity-00&limit=20` sequentially. Two warmup rounds are excluded from percentile summaries, then the configured repeat count is measured for each endpoint. Raw HTTP samples preserve method, endpoint, status, elapsed time, response bytes and SHA-256; final response examples are retained. Direct loopback connections do not use proxies or follow redirects. Non-200 responses, foreign-scope rows and invalid response contracts fail the run rather than silently dropping samples.

The dashboard's summary/events reflect its process-local recorder; operation-log reads shared durable SQLite history. Once concurrent writes and recalls finish, an isolated GET-only round verifies that the operation-log row count is unchanged. This is bounded actual HTTP-read concurrency evidence, not browser rendering, SSE behavior, authenticated dashboard access, or a sustained-load test. The seed scale counts events plus Claims, **not** operation-log rows: the operation history is generated by the bounded workload. HTTP latency includes opening a new loopback connection and reading the response. Extra writes and a distinct phase mean its timings and final database size must not be pooled with the default-only observations. Default behavior and datasets remain unchanged when the flag is absent.

`EXPLAIN QUERY PLAN` output covers explicitly labeled literal/FTS candidate primitives; it is not falsely presented as the complete application query plan. The full retrieval implementation also applies scope/status/literal rechecks, relevance/type selection and provenance mapping. Plans are obtained using Python’s reported SQLite version, which may differ from the SQLite bundled by the Rust/SQLx binary; they cannot establish that binary’s exact execution plan. In particular, a good Python primitive plan does not rule out a repeated-probe planner regression in the bundled runtime. Actual MCP timings remain the runtime evidence.

A valid historical comparison must build the exact historical commit (for example `11f9bd55cfe8cd11530406b563fc64a53e2f4506`), retain its binary checksum and report separately, and use the same fixture hashes, hardware/runtime session, build profile, repeats, and workload. A previous number from a different run is not a controlled baseline. Indexed and historical selection policies may differ; report that alongside timing and do not infer equivalence solely from response counts. Short Chinese terms can still require scoped scans. These are observations, not an SLA, universal scalability result, or a promise of better model behavior.

## Saved observations

See [2026-10-09 measured evidence](evaluation-evidence/README.md), including the intermediate indexed regression that the benchmark exposed and the fixed path rerun. This preserves failures as well as successful measurements; source attribution and host-load limits are explicit.

The separate [schema 6 evidence](evaluation-evidence/schema6/README.md) reruns the unchanged task/query selections and capacity seeds against a newly frozen default-feature binary. It preserves the temporal-metadata packing cost, the observed slower revision-chain result in the designated pair, a corrected smoke-fixture mistake, and a separately measured actual loopback HTTP concurrency workload. Prior schema 5 reports remain historical artifacts, unchanged; the paired schema 5 binary was verified and rerun rather than relabeling old timings.

The final harness additionally reports `reservation_acquisition_probe`: a direct Python SQLite contender times only its `BEGIN IMMEDIATE` acquisition while a separate connection holds a known reservation, then both roll back. This distinguishes acquisition elapsed from the existing full MCP write-request delay. It includes SQLite busy-handler scheduling and statement overhead, uses the separately reported Python SQLite version, and is not internal Rust lock telemetry or a pure scheduler-free wait duration. A regression verifies no source-file change from this probe; no latency threshold is used as a correctness assertion.

Final-stage capacity runs keep raw-recall timings separate and additionally time `build_task_context` for selective ASCII, short CJK and revision-chain queries (two warmups, configured repetitions, limit20, 16,384-byte complete-result budget). Each measured response must satisfy exact byte accounting and scope checks. These synthetic ledgers measure bounded status/source-inspection overhead but contain no large rich-Episode population; separate targeted Episode fanout/scope fixtures cover that mechanism. The original task evaluator still uses its unchanged 1,800-byte budget. Do not pool these two workloads or substitute either for real-model task quality.
